## El export PNG del view — 2 bugs reales encontrados y arreglados en la propia verificación

El diseño original (documentado en el plan) rasterizaba el DOM real de la card vía
`<svg><foreignObject>` (la misma familia de técnica que ya usa `exportarSvgComoPng` para los
charts). Probado con datos reales (ver «Verificado» abajo), **falló de las dos formas que el plan
ya anticipaba como riesgo, en ese orden**:

1. **Parse XML roto, 100% de las veces**: el CSS de Tailwind v4 trae reglas `@property` con
   descriptores tipo `syntax: "<color>"` — el `<` literal, embebido crudo dentro de un `<style>`
   XML, rompe el documento (`parsererror` de columna 1792, "Opening and ending tag mismatch").
   `img.onerror` no logueaba nada → fallo completamente silencioso, cero pista sin instrumentar el
   `evaluate()` a mano. Fix intentado: envolver el CSS en `<![CDATA[...]]>`.
2. **Con el XML ya válido, canvas "tainted" el 100% de las veces igual**: Chrome marca como
   tainted cualquier canvas rasterizado desde un `foreignObject` con contenido HTML — confirmado
   que NO es por fuentes/imágenes externas (se repitió sacando `@font-face`/`url()` del CSS
   embebido, mismo resultado). Es una limitación conocida de la técnica en sí (por eso existen
   librerías como html2canvas), no un bug de este código puntual.

**Decisión (fallback ya documentado en el plan de esta sesión para este caso exacto)**: se
abandonó por completo la rasterización del DOM y se reescribió `exportarNodoComoPng` →
**`exportarViewComoPng`** (`src/lib/chart-export.ts`) — dibuja la placa A MANO con
`ctx.fillText`/`ctx.fillRect` sobre un `<canvas>` limpio (grano, dirección, confianza, horizonte,
fecha, tesis con word-wrap, a favor/en contra, acción, invalidación, pie "ROFO AGRO"), usando los
colores reales del tema vigente (`getComputedStyle(--pos/--neg/--neu/--panel/--ink/...)` — leer
variables nunca tainta nada). Cero riesgo de taint (el canvas nunca recibe una imagen/HTML
externo) y cero dependencia de que el CSS del documento sea válido como XML. `ViewExportButton`
pasa de recibir un `cardId` (DOM) a recibir los datos semánticos ya armados (`ViewExportData`,
tipo nuevo) — más robusto y más simple que intentar leer el DOM del lado del botón.

## Decisiones tomadas (y por qué)

- El TC para el cross-cálculo $↔USD en Arbitrajes es el **implícito de la pizarra CAC del propio
  grano** (no un TC genérico) — reproduce la relación que CAC ya publica para ESE grano; `tcBna`
  queda como respaldo, no como default.
- La liquidez de Pases se filtra ANTES de armar los pares (adentro de `getPases()`), no después —
  evita construir un pase con una pata que después se oculta a medias.
- Caja usa la posición MÁS CERCANA cuando hay dos campañas vivas del mismo mes, no la primera del
  array — evita depender del orden de `g.rows`.
- El export del view se resolvió con la salida hand-drawn en vez de insistir en variantes de la
  técnica foreignObject (filtrar más CSS, CORS, etc.): el taint de Chrome es estructural a la
  técnica con HTML adentro, no a un detalle de esta implementación — cualquier variante iba a
  volver a fallar.

## Trampas descubiertas (para la próxima sesión)

- **`foreignObject`→canvas SIEMPRE tainted en Chrome cuando el contenido es HTML** (no una config
  puntual) — si un futuro pedido pide exportar OTRO bloque HTML complejo a PNG del lado del
  cliente, no reintentar esta técnica: ir directo al patrón hand-drawn en canvas, o a un export
  server-side (como ya hace `/informes/plantilla/*` con Playwright).
- `noUncheckedIndexedAccess` (repo-wide desde el L3 del 24/07) atrapa cualquier indexado nuevo de
  `Record<string,X>` sin key literal — pasó con `GRANO_EMOJI[v.grano]` en `view/page.tsx`
  (`?? ""` resolvió).
- El servidor de verificación (`npm run start -p 3100`) hay que reconfirmar SIEMPRE con
  `pgrep -f "next-server \(v" | xargs ps -o pid,lstart` antes de confiar en un screenshot — un
  `kill`/rebuild sin verificar el PID nuevo puede estar sirviendo el build viejo (ya documentado en
  R1, se repitió el chequeo acá).
