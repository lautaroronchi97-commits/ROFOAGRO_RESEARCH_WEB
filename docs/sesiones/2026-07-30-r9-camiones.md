## Arquitectura (por qué se movió el fetch a `page.tsx`)

`plantas-panel.tsx`/`camiones-panel.tsx` eran 2 Server Components `async` independientes — no
podían compartir estado de cliente (filtro de grano, tabla abierta) entre sí. Se **borraron** y
su lógica de fetch pasó a `page.tsx` (`Promise.all` de `getCamionesPlantas()` + `getCamiones()`),
que pasa los datos ya resueltos a un client component único (`camiones-client.tsx`) que renderiza
los 2 paneles y sostiene el estado compartido. `senal-camiones.tsx` (solo-mesa, sin necesidad de
compartir estado) sigue como Server Component sibling, sin tocar.

## Decisiones tomadas (y por qué)
- **KPI "producto líder" solo con filtro en "Todos"**: con un grano ya elegido en el chip bar,
  mostrar "líder: {ese mismo grano}" es trivial/redundante — se oculta en vez de mostrar un dato
  vacío de contenido.
- **Modo campaña deshabilitado sin un grano elegido**: la campaña agrícola depende del mes de
  arranque de CADA producto (marzo maíz, abril soja, diciembre trigo/cebada, febrero girasol) —
  sumar TODOS los productos no tiene un único calendario de campaña válido.
- **Zonas se suman (no se promedian) al pasar a modo campaña**: "zonas elegidas" pasa a ser un
  filtro sobre qué zonas entran al total nacional/parcial de esa campaña, evitando una leyenda
  con zona×campaña (demasiadas líneas para leer).
- **Campañas disponibles se calculan SIEMPRE sobre las 4 zonas** (no las elegidas en ese momento):
  así tocar el filtro de zonas no le mueve el piso a qué campañas eligió ver el usuario.

## Trampas descubiertas (para la próxima sesión)
- El linter de este repo corre con las reglas del **React Compiler** (`react-hooks/set-state-in-
  effect`, `react-hooks/immutability`), más estrictas que `rules-of-hooks` plano: llamar
  `setState` dentro de un `useEffect` para "resetear estado derivado cuando cambia una prop" se
  marca error — hay que usar el patrón de React ("ajustar estado durante el render", comparando
  contra un `useState` que guarda el valor anterior) en vez de un efecto. Y declarar una función
  auxiliar (`function X(){}`) DESPUÉS de un hook que ya la usa en un callback también se marca
  error en algunos casos (no en todos — no quedó claro el patrón exacto), aunque el hoisting de JS
  lo permitiría en tiempo de ejecución: más seguro declarar los helpers ANTES del hook que los usa.
- Confirmado de nuevo (van 2+ sesiones): un `rm -rf .next && npm run build` no alcanza si el
  SERVIDOR de verificación anterior sigue vivo apuntando al build viejo — hay que matar el proceso
  `next-server` (no solo `npm run start`, que a veces deja un hijo huérfano) antes de levantar el
  nuevo, o Playwright pega contra chunks con hash de un build que ya no existe en disco (500 +
  MIME `text/plain`).
